    实验提交¶

    本次实验提交什么

    • 实验报告 ：回答实验步骤中的问题，并简要写清实验设计思路与运行结果。
    • 实验代码 ：只提交 commit.patch， 不需要提交整个工程目录 。
    • commands.gdb ：请将它放在 xv6-oslabs-hitsz 目录中，并执行 git add commands.gdb。这样导出的 commit.patch 中也会包含这个文件的改动。

    提交前请先自己检查 commit.patch

    至少请你自己检查一次：commit.patch 能否在干净的实验初始代码上成功还原出你的实验结果。

    如果提交上来的 commit.patch 不能成功应用，或者应用后无法恢复出应有结果，老师在评测和检查时就无法正确还原你的实验内容，这通常会影响评分。

    检查方法可直接跳到：如何检查 commit.patch 能否还原你的实验结果。

    【实验课件、报告模板与工具】统一放在实验指导书首页「实验相关链接」 → 实验课件、报告及工具。

    1. 先看提交要求¶

    1.1 实验报告¶

    实验报告会纳入评分。建议至少包含以下内容：

    • 回答实验步骤中的问题；
    • 简要说明 sleep、pingpong、find 的实现思路；
    • 给出关键运行结果或测试结果；
    • 简要说明启动流程实验中你观察到了什么。

    实验报告也是判断你是否真正理解实验的重要依据，因此不要只放代码截图。

    1.2 实验代码¶

    代码部分只需要提交一个 commit.patch 文件。

    也就是说，你最终提交到作业平台的通常就是：

    • 实验报告
    • commit.patch

    2. 推荐提交流程¶

    下面这些命令都在 Linux 终端 中执行，且当前目录应为 xv6-oslabs-hitsz（也就是能看到 Makefile 的那个目录）。

    第 1 步：先完成实验并通过基本测试¶

    完成 sleep、pingpong、find 后，建议先执行：

    ./grade-lab-util sleep
./grade-lab-util pingpong
./grade-lab-util find
make grade

    如果环境提示：

    /usr/bin/env: 'python': No such file or directory

    可以执行：

    sudo ln -s /usr/bin/python3 /usr/bin/python

    然后重新运行测试。

    第 2 步：准备 commands.gdb¶

    做完启动流程实验后，请将 commands.gdb 放在 xv6-oslabs-hitsz 目录中，并确认它可以在 GDB 中使用：

    source commands.gdb

    如果你需要回看 commands.gdb 的要求与导出方法，可参考：

    • 实验概述中的启动流程实验要求
    • GDB 调试指南

    第 3 步：提交当前修改¶

    确认当前实验内容已经完成后，执行：

    git add .
git commit -m "lab1 finished"

    如果这是你第一次在这台机器上使用 Git，还需要先配置：

    git config --global user.name "你的用户名"
git config --global user.email "你的邮箱"

    用户名和邮箱怎么填？

    如果你这次只是为了在本地完成 git commit 并导出 commit.patch，用户名和邮箱只要不留空即可。

    如果你后面还打算把代码推送到自己的远程仓库，建议这里填写你自己的常用 Git 用户名，以及与远程平台账号关联的邮箱。这样远程仓库里的提交记录才更容易正确显示作者信息。

    第 4 步：导出 commit.patch¶

    执行：

    make diff

    执行成功后，项目目录下会生成 commit.patch。

    为什么前面一定要先 commit？

    make diff 比较的是你当前提交版本与实验初始版本之间的差异。如果你没有先 commit，导出的内容就可能不完整，甚至不符合提交要求。

    第 5 步：打包提交¶

    最后提交：

    • 实验报告
    • commit.patch

    即可。

    3. 提交前自检¶

    在上传前，建议你至少检查下面几项：

    • make grade 已经通过，或至少你已经确认主要功能正常；
    • commands.gdb 已放在项目目录中，并能被 source commands.gdb 读取；
    • commit.patch 已成功生成；
    • 请至少自己检查一次：commit.patch 能否在干净的实验初始代码上成功还原出你的实验结果 ；
    • commit.patch 中包含了你本次实验真正需要提交的改动；
    • 自己知道 sleep、pingpong、find 和启动流程实验分别做了什么，能够说明关键思路。

    4. 如何检查 commit.patch 能否还原你的实验结果¶

    先理解两个词：

    • commit.patch：它不是完整工程，而是一份 改动清单 ，记录了你相对实验初始代码修改了哪些文件、增加了哪些代码、删除了哪些代码。
    • git apply commit.patch：它的作用，就是把这份“改动清单”重新应用到一份干净的初始代码上。

    所以，这一步检查的意思其实很简单：

    回到一份干净的实验初始代码，再试一次能不能仅靠 commit.patch 恢复出你的实验结果。

    如果能够成功应用，并且 make grade 也能通过，就说明你提交的 commit.patch 通常是可靠的。

    下面这些命令都在 Linux 终端 中执行，当前目录仍然是 xv6-oslabs-hitsz。

    推荐做法¶

    1. 先把 commit.patch 临时复制到项目目录外，避免切换版本后找不到：

      cp commit.patch ../commit.patch

    2. 如果你当前还有未提交的其它改动，先暂存起来：

      git stash

    3. 切换到实验初始版本：

      git checkout util-26-fall

      课程提供的各实验初始代码 Git 标签名如下（它们与日常开发分支名称不同）：

      • Lab1：util-26-fall
      • Lab2：syscall-26-fall-v2
      • Lab3：lock-26-fall-v2
      • Lab4：pgtbl-26-fall

      如果提示找不到 util-26-fall，再执行：

      git fetch --tags

    4. 把刚才备份的 commit.patch 复制回当前目录：

      cp ../commit.patch .

    5. 应用补丁：

      git apply commit.patch

      如果这一步没有报错，就说明这份补丁至少可以正确打到当前这份初始代码上。

    6. 重新测试：

      make grade

    7. 如果上面两步都顺利完成，也就是：

      • git apply commit.patch 没有报错；
      • make grade 通过，或至少主要测试通过；

      那就说明：老师通常也可以用你的 commit.patch 还原出实验结果。

    8. 检查完成后，切回你的开发分支：

      这里以 Lab1 为例，开发分支名是 util。如果你检查的是其他实验，请换成对应的开发分支名，例如 Lab2 使用 syscall，Lab3 使用 lock，Lab4 使用 pgtbl。

      git checkout -f util

    9. 如果你前面执行过 git stash，最后恢复现场：

      git stash pop

    常见问题¶

    git apply commit.patch 找不到文件怎么办？

    通常是因为你切到 util-26-fall 后，当前目录里没有 commit.patch。最稳妥的做法，就是像上面那样先执行 cp commit.patch ../commit.patch，检查时再执行 cp ../commit.patch . 复制回来。

    git apply commit.patch 报错说明什么？

    一般说明这份 commit.patch 不能完整对应当前的实验初始代码。常见原因是：补丁内容不完整、补丁是从错误分支导出的，或者补丁里混入了不该提交的内容。

    生成 commit.patch 后，还需要再 commit 才能切换分支吗？

    一般 不需要 。如果你在执行 make diff 之前，已经把实验代码 commit 过，那么这时真正需要提交的代码改动已经被记录下来了。

    生成出来的 commit.patch 只是一个导出的补丁文件，通常 不要再为它单独执行 git add 或 git commit 。

    更稳妥的做法是：先执行 cp commit.patch ../commit.patch 把它临时复制到项目目录外，再切换到 util-26-fall 或其他标签。

    只有在你后来又继续改了代码、导致工作区不干净时，才需要先 commit 或 git stash，再切换分支。

    commit.patch 不要再被 Git 跟踪

    生成 commit.patch 之后，不要再执行 git add commit.patch。否则补丁里可能又把 commit.patch 自己打进去，后续 git apply 就容易出问题。

    5. 最小 Git 流程¶

    如果你这次只关心“怎么交实验”，记住下面这几条命令就够了：

    git add .
git commit -m "lab1 finished"
make diff
