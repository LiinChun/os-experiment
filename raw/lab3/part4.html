    1. 锁的基本实现原理¶

    在 kalloc.c、bio.c 等代码里，你会经常看到 acquire() 和 release()。它们看起来像普通函数，但真正实现“同一时刻只能有一个 CPU 进入临界区”并不简单。先看一个最朴素、但实际上错误的实现：

    void acquire(struct spinlock *lk) // does not work!
{
    for(;;) {
        if(lk->locked == 0) {
            lk->locked = 1;
            break;
        }
    }
}

    这个版本的问题在于：“检查锁是否空闲” 和 “把锁设为已占用” 不是一个不可分割的原子动作。

    这个版本为什么会出错

    • 假设 lk->locked 一开始是 0，也就是锁空闲；
    • CPU0 和 CPU1 几乎同时执行 acquire()；
    • 两个 CPU 都可能先读到 lk->locked == 0；
    • 然后它们又都把 lk->locked 写成 1；
    • 结果就是：两个 CPU 都以为自己成功拿到了锁。

    所以，光靠“先判断，再写入”的普通 C 代码还不够。这里必须借助硬件提供的 原子读改写指令。

    在 RISC-V 中，常见的一条相关指令是 amoswap。它会在 一条指令 里完成“读出旧值 + 写入新值”，并保证在这次操作完成之前，其他 CPU 不会把同一地址改坏。

    amoswap指令和__sync_lock_test_and_set

    可以把 __sync_lock_test_and_set() 粗略看成 amoswap 的一个上层封装：

    int __sync_lock_test_and_set(volatile int *ptr, int value);

    可以把它的内部行为粗略理解成下面这样：

    int __sync_lock_test_and_set(volatile int *ptr, int value)
{
    int old = *ptr;
    *ptr = value;
    return old;
}

    但要注意：上面只是 行为上的伪代码。真正实现时，编译器会把它翻译成 amoswap 这类 原子交换指令，保证“读旧值 + 写新值”是一次不可分割的操作。

    在 acquire() 里，真正执行的是：

    __sync_lock_test_and_set(&lk->locked, 1)

    它的意思是：原子地把 lk->locked 设为 1，并返回设置前的旧值。

    注意：这里的返回值 不是“成功/失败状态码”，而是“调用前 lk->locked 原来是多少”。

    • 返回 0：说明调用前 lk->locked 原来就是 0，也就是锁空闲；这次调用把它改成了 1，因此当前 CPU 成功拿到锁。
    • 返回 1：说明调用前 lk->locked 原来已经是 1，也就是锁已经被别人占着；所以当前 CPU 这次没拿到锁，只能继续等。

    // Acquire the lock.
// Loops (spins) until the lock is acquired.
void
acquire(struct spinlock *lk)
{
    push_off(); // 先关中断，避免持有自旋锁时被中断打断而死锁
    if(holding(lk))
        panic("acquire"); // 不允许同一个 CPU 重复获取同一把锁
    __sync_fetch_and_add(&(lk->n), 1); // 统计这把锁被尝试获取了多少次
     // On RISC-V, sync_lock_test_and_set turns into an atomic swap:
     //   a5 = 1
     //   s1 = &lk->locked
     //   amoswap.w.aq a5, a5, (s1)
     while(__sync_lock_test_and_set(&lk->locked, 1) != 0) { // 原子地尝试把 lk->locked 设为 1
         __sync_fetch_and_add(&lk->nts, 1); // 旧值不是 0，说明锁已被占用，记录一次自旋等待
     }

     // Tell the C compiler and the processor to not move loads or stores
     // past this point, to ensure that the critical section's memory
     // references happen after the lock is acquired.
     __sync_synchronize(); // 保证必须先成功拿到锁，后面才能访问临界区里的共享数据
     // Record info about lock acquisition for holding() and debugging.
     lk->cpu = mycpu(); // 记录当前持有这把锁的是哪个 CPU
}

    这里最关键的是 while 循环中的这句：

    __sync_lock_test_and_set(&lk->locked, 1)

    它不是普通的“先读再写”，而是一个 原子交换。可以把它分成两种情况来理解：

    • 当执行这条原子交换前，lk->locked 原来为 0 时：函数返回旧值 0，同时把 lk->locked 写成 1。这说明本次成功拿到了锁，于是退出 while。

    • 当执行这条原子交换前，lk->locked 原来为 1 时：函数返回旧值 1，同时仍把 lk->locked 写成 1。这说明锁已经被别人持有，所以当前 CPU 只能继续在 while 里自旋等待。

    代码里还有几句容易看见但不必在这一页死磕的辅助语句：

    • push_off()：避免持锁期间被中断打断，从而引出死锁；
    • __sync_fetch_and_add(&(lk->n), 1) / __sync_fetch_and_add(&(lk->nts), 1)：记录统计信息，后面 kalloctest 会用到；
    • __sync_synchronize()：保证必须先成功拿到锁，后面才能访问临界区里的共享数据；
    • lk->cpu = mycpu()：方便 holding() 和调试。

    如果你现在已经能回答下面这个问题，这一节就算读明白了：

    为什么“普通判断 + 普通赋值”不够，而必须依赖 __sync_lock_test_and_set() 这类原子操作？

    注：以上解释可以对照 xv6 book 的 Locking 章节阅读。

    2. 锁与kalloc¶

    kalloc 里为什么一定要给 freelist 加锁？核心原因只有一句：

    freelist 是所有 CPU 共享的一条空闲页链表。

    只要多个 CPU 会并发地修改它，就必须保证“同一时刻只有一个执行流在改这条链表”。

    // Allocate one 4096-byte page of physical memory.
// Returns a pointer that the kernel can use.
// Returns 0 if the memory cannot be allocated.
void *
kalloc(void)
{
 struct run *r;

 acquire(&kmem.lock);
 r = kmem.freelist;
 if(r)
   kmem.freelist = r->next;
 release(&kmem.lock);

 if(r)
   memset((char*)r, 5, PGSIZE); // fill with junk
 return (void*)r;
}

    如果这里没有锁，会发生什么

    • CPU0 和 CPU1 可能同时读到相同的 kmem.freelist 头结点；
    • 然后它们都把同一张页当成“自己刚分配到的页”返回出去；
    • 结果就是：两个执行流错误地共享了同一张物理页。

    这会直接破坏内存分配器最基本的正确性要求：

    • 一张空闲页在同一时刻只能被分配给一个使用者；
    • freelist 的头指针更新必须是串行的。

    kfree() 也是同理。它虽然做的是“把页塞回链表”，但本质上仍然是在改共享链表；如果没有锁，也可能把链表接坏，或者把某张页重复插回去。

    3. 锁与bio¶

    bio.c 比 kalloc.c 更复杂，因为它同时需要保护：

    • 整个 buffer cache 的共享管理结构；
    • 某一个具体缓存块里的数据访问。

    因此 xv6 在这里同时使用了两种锁：

    • 自旋锁 bcache.lock
    • 睡眠锁 b->lock

    3.1 自旋锁 bcache.lock¶

    bcache.lock 保护的不是某一块具体数据，而是 整个缓存系统的公共元数据。原版 xv6 中，它主要保护这些内容：

    • 缓存块链表 bcache.head；
    • refcnt 这类共享计数；
    • dev、blockno、valid 这类“某个 buf 当前代表哪个磁盘块”的元数据。

    因此，在原版 xv6 里：

    • bget() 在查找或分配缓存块时，需要持有 bcache.lock；
    • brelse() 在修改 refcnt、并按 LRU 规则调整链表位置时，需要持有 bcache.lock；
    • bpin() / bunpin() 在修改 refcnt 时，也需要持有 bcache.lock。

    自旋锁的特点是：

    • 临界区通常比较短；
    • 拿不到锁时不会睡眠，而是一直忙等（spin）；
    • 适合保护“改几个共享字段就结束”的短操作。

    下面是 xv6 中自旋锁最关键的获取 / 释放实现：

    void
acquire(struct spinlock *lk)
{
  push_off(); // 持有自旋锁期间先关中断
  if(holding(lk))
    panic("acquire"); // 不允许重复获取同一把锁

  while(__sync_lock_test_and_set(&lk->locked, 1) != 0) // 原子地尝试把 lk->locked 设为 1
    ;

  __sync_synchronize(); // 内存屏障，保证临界区访问不会跑到锁外
  lk->cpu = mycpu();    // 记录当前持锁 CPU
}

void
release(struct spinlock *lk)
{
  if(!holding(lk))
    panic("release"); // 只有持锁者自己才能释放

  lk->cpu = 0;                  // 清除持锁 CPU 记录
  __sync_synchronize();         // 保证临界区内的写入先完成
  __sync_lock_release(&lk->locked); // 原子地把 lk->locked 恢复为 0
  pop_off();                    // 恢复中断状态
}

    可以把它抓成两步：

    • acquire()：反复用原子操作尝试把 lk->locked 设为 1，直到成功为止；
    • release()：先清理持锁信息，再把 lk->locked 原子地恢复为 0。

    3.2 睡眠锁 b->lock¶

    b->lock 保护的是 某一个具体 buf 的独占使用过程。更准确地说，它保护的是：

    • 谁正在独占使用这个 buf；
    • 这个 buf 里的 data[BSIZE] 是否能被安全读写。

    原版 xv6 里，常见的使用方式是：

    • bget() 在找到对应的 buf 之后，会进一步获取 b->lock；
    • bwrite() 要求调用者已经持有这个 buf 的睡眠锁；
    • brelse() 在释放缓存块时，会释放这个睡眠锁。

    和自旋锁不同，睡眠锁在拿不到时会让线程睡眠，把 CPU 让出去，因此更适合“持锁时间可能稍长”的场景。

    buf 这里之所以更适合睡眠锁，是因为“使用一个缓存块”的过程往往不只是改一下标志位，而可能持续较长时间：

    • 调用者可能会在持锁期间读写 data[BSIZE]；
    • 还可能伴随磁盘 I/O、文件系统路径上的后续处理；
    • 如果这里也用自旋锁，那么别的线程拿不到锁时就只能一直空转，浪费 CPU。

    下面是 xv6 中睡眠锁最关键的获取 / 释放实现：

    void
acquiresleep(struct sleeplock *lk)
{
  acquire(&lk->lk); // 先用内部自旋锁保护睡眠锁状态
  while (lk->locked) {
    sleep(lk, &lk->lk); // 如果已经被占用，就睡眠等待，并临时放开 lk->lk
  }
  lk->locked = 1;         // 标记睡眠锁已被占用
  lk->pid = myproc()->pid; // 记录当前持锁进程
  release(&lk->lk);       // 状态更新完后释放内部自旋锁
}

void
releasesleep(struct sleeplock *lk)
{
  acquire(&lk->lk); // 修改状态前先拿内部自旋锁
  lk->locked = 0;   // 标记睡眠锁已释放
  lk->pid = 0;      // 清除持锁者记录
  wakeup(lk);       // 唤醒等待这把睡眠锁的进程
  release(&lk->lk); // 释放内部自旋锁
}

    这里要特别注意一件事：睡眠锁自己内部，仍然是靠一把自旋锁 lk->lk 来保护其状态字段。

    也就是说：

    • 外层效果上，它是“拿不到就睡眠”的锁；
    • 但内部实现上，它仍然需要先用短临界区的自旋锁，保护 locked / pid 这些共享状态。

    自旋锁和睡眠锁的区别

    • spinlock：适合短临界区；拿不到时忙等；在 xv6 中持有期间会关中断。
    • sleeplock：适合持锁时间较长的场景；拿不到时会睡眠让出 CPU；不能在中断上下文中使用。
    • bio 里两种锁并存，不是重复设计，而是因为它们保护的对象不同：bcache.lock 保护“全局管理信息”，b->lock 保护“单个缓存块的数据使用”。

    4. 测评程序 kalloctest 对锁的检测¶

    kalloctest 关心的不是“你有没有加锁”，而是“你的锁竞争是否严重”。

    前面 acquire() 代码 里有两个和统计有关的字段：

    • lk->n：也就是输出中的 #acquire，表示这把锁一共被尝试获取了多少次；
    • lk->nts：也就是输出中的 #fetch-and-add，表示有多少次尝试获取锁时，发现锁已经被别人占着，只能继续自旋等待。

    可以这样理解：

    • #acquire 大，不一定是坏事，它只能说明这把锁被频繁使用；
    • #fetch-and-add 大，才更能说明“很多 CPU 经常撞到一起抢同一把锁”。

    所以 Lab3 要优化的重点，并不是把锁删掉，而是：

    • 让不同 CPU 尽量少去争抢同一把锁；
    • 让那些本来可以并行的操作，不要无谓地串到一起。

    测试输出真正想说明什么

    如果某把锁的 #fetch-and-add 很大，通常意味着：

    • 这把锁是热点；
    • 很多时间花在了自旋等待上；
    • 你的并发度正在被这把锁限制。

    因此，kalloctest 的目标不是“完全没有锁”，而是“把热点锁的竞争降下来”。
