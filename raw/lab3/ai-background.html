    AI 推理的数据背景¶

    阅读本页前，先看附加题要求。本页解释后续模型与 KV 任务使用的基本概念；不要求实现真实大模型或 GPU 算子。

    实验背景：从零理解 AI 推理数据¶

    在真实的 AI 推理服务中，瓶颈不只来自模型计算。一个 worker（工作进程）还要读取模型参数和 embedding（嵌入向量），申请、释放保存中间状态的页面，把 KV cache（键值缓存）写入较慢的存储层并在需要时恢复，同时与其他 worker 共享 CPU、内存、文件系统和 buffer cache。本附加题在没有 GPU 的 xv6 CPU 环境中，用一个小型确定性模型模拟这条数据通路。

    本节为 AI 推理服务附加题 提供必要的背景知识。如果只完成 Lab3 原题任务一（kalloc）和任务二（bcache），可以先跳过本节，开始附加题前再回来阅读。你不需要先学过机器学习，也不需要记住完整的 Transformer 公式。阅读时只需抓住一个问题：一个推理请求的数据从哪里来，经过哪些步骤，最后如何体现为 xv6 中的操作系统问题？

    先分清“训练”和“推理”¶

    神经网络模型的生命周期可以粗略分为两个阶段：

    • training（训练）：使用大量样本反复调整模型参数。训练需要计算损失、梯度和参数更新，通常非常耗费算力；
    • inference（推理）：参数已经确定，系统接收用户输入并计算输出。推理一般只读取参数，不再修改它们。

    本实验只研究 inference（推理）阶段。

    • modelprep：生成内容确定的模型文件，作用相当于把“已经训练好的参数”写入 xv6 文件系统；
    • aiinfer：AI 推理程序再读取这些文件处理请求。本实验不训练模型、不做反向传播，也不要求编写 GPU 程序。

    为什么操作系统实验还要关心推理？因为推理不只是数学计算。一个服务还要完成模型读取、内存分配、缓存管理、请求隔离、临时状态保存和并发调度。即使模型算子足够快，如果数据不能及时到达 CPU，服务仍然会变慢。

    常见误区：modelprep 不是训练程序

    modelprep 只是生成可重复验证的教学数据。它不从样本中学习参数，也不改变后续计算规则。把它看作“制作模型文件的工具”更准确。

    你现在应当理解

    AI 附加题的模型加载和 KV 持久化都发生在推理阶段。我们不评价模型是否聪明，只评价同一输入下数据是否正确流动，以及优化后操作系统路径是否更高效。

    检查理解：为什么模型参数通常可以被多个请求共享？

    推理时模型参数已经固定，多个请求只读同一组参数。只要缓存实现不修改其内容，就没有必要为每个请求复制一套参数。请求产生的 KV cache 则不同，它包含该请求自己的历史状态，不能混用。

    文本怎样变成 token¶

    计算机最初收到的是字符串，例如“系统快”。模型无法直接对文字进行整数或矩阵运算，所以会先通过 tokenizer（分词器） 把文本切成 token（词元），再在固定的 vocabulary（词表） 中查询编号。

    下面是假设性的教学例子：

    文本片段 token 编号
    “系统” 5
    “快” 12
    句子结束标记 3

    于是字符串“系统快”可以表示为整数序列 [5, 12, 3]。不同模型的 tokenizer 可能把同一句话切成完全不同的 token；token 既不保证对应一个汉字，也不保证对应一个完整单词。

    本实验不实现真实 tokenizer。为了让测试结果可重复，prefill_request() 会根据 worker 编号和请求编号生成一个初始 token：

    token = (worker * 7 + request * 13) % AI_VOCAB;

    其中：

    • worker：当前 worker 的编号；
    • request：当前请求的编号；
    • 7：worker 编号的权重；
    • 13：request 编号的权重；
    • AI_VOCAB：词表大小，本实验中为 32。

    这里的 token 仍只是 0 到 AI_VOCAB - 1 的整数编号；每个 step 结束后，函数还会根据本轮计算结果更新下一个 token。暂时只需把它看作“测试输入的编号”，prefill_request() 的完整处理流程见 Prefill 与 Decode。这里 AI_VOCAB = 32，表示教学词表中只有 32 个可用编号。

    常见误区：token 不是字符串，也不是向量

    token 在后续计算中首先只是一个整数编号。编号 5 比编号 3 大，并不表示它的语义更多或更重要。要把编号变成可计算的特征，还需要 embedding。

    检查理解：token 编号为什么不能直接表达语义距离？

    编号只是词表中的位置。例如编号 5 和 6 相邻，不代表二者语义相似；编号 5 和 30 相距很远，也不代表语义差异更大。

    embedding：把编号查成向量¶

    Embedding（嵌入向量） 可以理解为一张查找表：输入 token 编号，得到一组数值。这组数值才会进入后续模型计算。

    继续使用刚才的例子，假设教学 embedding 只有两个维度：

    token embedding
    5 [1, 2]
    12 [-1, 3]
    3 [2, 0]

    查询后，[5, 12, 3] 就变成三个二维向量。真实模型的维度往往大得多，本实验使用 AI_DIM = 8，表示每个向量有 8 个分量；这里只保留“根据 token 或请求读取 embedding 数据并生成特征”这一过程。

    你现在应当理解

    token 是编号，embedding 是由编号查到的向量。二者不是同一概念。

    模型参数与模型分片¶

    model parameters（模型参数） 是在 training 阶段学习得到、在 inference 阶段读取使用的一组数值。它们决定输入向量怎样被逐层变换。对于本实验，你可以把它们理解成“推理前已经固定、推理时大量读取的只读数据”。

    真实模型可能有数十亿个参数，单个文件不便于按需加载、并行读取或分布到不同设备。因此工程系统常按层、设备或文件区间切成 shard（分片）。分片不是新的数学概念，只是存储和调度单位发生了变化。

    下面是通用的 embedding 分片示意，不是本 workload 的编号公式。Embedding 表也可以用同样的方式切分。把它看成“每一行对应一个 token”的大表：第 0 行存 token 0 的向量，第 1 行存 token 1 的向量，以此类推。如果每个 shard 容纳 4 行，那么 shard 0 存 token 0～3，shard 1 存 token 4～7；查询 token 6 时，先定位到 shard 1，再读取该 shard 中的第 2 行。一般来说，给定 token 编号 t 和每片容量 K，分片编号为 t / K，片内位置为 t % K。这样按连续编号切分后，需要某一段 token 时只读取对应分片，也便于分片级缓存和并行访问。

    本实验使用两类分片：模型分片 m00～m36，以及 embedding 分片 e00～e36；两类文件各有 37 个，每个文件 1024 字节。在代码中，prefill_request() 的每个 step 都会调用 shard_feature()，先读取一个 mXX 模型分片，再读取一个 eXX embedding 分片。两个分片编号的计算可以直接对照代码看：

    model_feature = shard_feature(...,
                              (request + step) % AI_MODEL_SHARDS, io);
embed_feature = shard_feature(...,
                              (worker * 11 + request * 7 + step) %
                              AI_EMBED_SHARDS, io);

    表达式得到的编号会补成两位文件名：例如模型编号 7 对应 m07，embedding 编号 12 对应 e12。两类分片的编号通常不同，但都来自各自的 0～36 范围。文件名使用 m07、e12 这类短格式，是因为 xv6 目录项的 DIRSIZ 较小。真实系统可能使用更长、包含层号或设备号的路径，本实验只保留 family 和 shard 编号。

    shard_feature() 负责按编号读取相应文件（或命中已有的用户态模型缓存），返回确定性的 model_feature 和 embed_feature。这不是完整的神经网络层，但保留了三种关键性质：

    1. 数据第一次必须来自文件系统；
    2. 同一分片会被同一 worker 的多个请求重复使用；
    3. 多个 worker 会并发访问相同只读工作集。

    为什么要做成文件，而不是直接写在 C 数组里？

    如果把数据编译进 aiinfer，读取时就不会经过 open()、read() 等文件系统调用，也不会经过 inode（索引节点）、buffer cache 和磁盘路径，因而无法观察 Lab3 原题任务二（bcache） 要优化的竞争。把数据放进 xv6 文件系统，才能让 workload（工作负载）真实施加存储压力。

    常见误区：分片编号不代表模型层编号

    m07 只是本实验的第 7 个模型数据文件。指导书不会把它解释成 Transformer 的第 7 层，因为代码没有建立这种对应关系。

    检查理解：为什么只读分片适合缓存，而 KV cache 不能用同样方式全局共享？

    只读分片的内容固定，同一编号的分片对所有请求都相同，因此可以按分片缓存并由多个请求复用。KV cache 则是根据特定请求的输入历史产生的中间状态，具有请求私有性，必须按请求隔离保存；若被多个请求直接全局共享，就可能导致上下文混淆、数据覆盖和并发访问问题。

    Prefill 与 Decode：一次请求的两个阶段¶

    自回归语言模型的推理通常可以粗略分成两个阶段：

    1. Prefill（提示词处理）：一次处理用户已经给出的上下文，为每个历史 token 计算供后续 Attention（注意力机制）使用的 query（查询向量）、key（键向量）和 value（值向量）；
    2. Decode（解码/逐 token 生成）：根据已有上下文生成下一个 token，再把新 token 加入上下文，继续下一轮。

    可以把二者类比为“先读完题目并做笔记，再逐步作答”。Prefill 读取整段输入并准备笔记；Decode 每次作答都要查阅之前的笔记。

    前文提到的 prefill_request() 就是 Prefill 阶段的代码实现。函数一开始记录请求的起始时间；随后循环 32 个 step。每一步读取一个模型分片和一个 embedding 分片，把得到的特征转换后分别写入 kv[step].key、kv[step].value，同时更新当前请求的 workspace.query。本轮结果还会用于生成下一个 token。循环结束后，函数记录 partial 和 KV checksum，供后续校验使用；它们不是额外的 KV 副本。32 组 key/value 组成一份 KV cache。随后 workload 把 KV 写入文件并释放原页面。恢复阶段的 decode_request() 只使用恢复后的 KV 执行 attention-style（类注意力）计算。

    一次请求的输入
  -> 初始化 token（本实验由 worker/request 编号确定）
  -> Prefill：按编号读取 mXX 模型分片和 eXX embedding 分片
  -> 计算 query、key、value
  -> 保存 key/value，形成 KV cache
  -> KV offload（卸载）：写入文件并释放原页面
  -> KV restore（恢复）：重新申请页面并读回 KV
  -> Decode：用 query 匹配历史 key，再读取 value

    你现在应当理解

    Prefill 负责为上下文准备 K/V；Decode 反复使用这些历史 K/V。AI 附加题的 KV 任务位于两者之间：把 Prefill 产生的 KV 保存到文件系统，并在 Decode 前恢复。

    Q、K、V 与 Attention 的最小例子¶

    Decode 需要回答：“当前这一步应该参考历史中的哪个位置？” Attention（注意力机制） 就是解决这个问题的一种计算方式，其中三个名字分别表示：

    • Query（Q，查询向量）：当前步骤“想找什么”；
    • Key（K，键向量）：每个历史位置“可以怎样被匹配”；
    • Value（V，值向量）：匹配到该位置后“真正取回什么信息”。

    先看一个二维整数例子。当前 query 为 [2, 1]，历史中有两个位置：

    历史位置 key value
    0 [1, 0] [8, 4]
    1 [0, 3] [2, 9]

    先用点积计算匹配分数：

    score(0) = [2, 1] · [1, 0] = 2*1 + 1*0 = 2
score(1) = [2, 1] · [0, 3] = 2*0 + 1*3 = 3

    位置 1 的分数更高，所以这个简化算法选择位置 1，并取回它的 value [2, 9]。请注意：key 用于匹配，value 才是匹配后读取的数据；二者即使维度相同，职责也不同。

    真实 Transformer 通常会计算缩放点积、softmax（归一化函数）权重以及多个 value 的加权和。本实验没有复刻完整浮点计算。decode_request() 使用 8 维整数 query 与 32 个 key 做点积，选择最高分位置，再把对应 value 混入确定性输出，并重复 32 轮以制造可测的 CPU 工作量。

    score(step) = query[0] * key[step][0]
            + query[1] * key[step][1]
            + ...
            + query[7] * key[step][7]

    这种简化不会改变实验关注的系统问题：Decode 必须等到正确 KV 到达；数据若读错、请求若混淆，最终输出和 checksum（校验和）就会改变。

    常见误区：本实验不是在测模型精度

    整数 attention-style（类注意力）计算的目标是产生可重复且依赖 KV 的输出，而不是模拟自然语言质量。不能用它比较模型能力，但可以用它检查数据通路等价，并留出可与预取重叠的计算时间。

    检查理解：为什么 KV cache 必须同时保存 key 和 value？

    Decode 会先用当前 query 与每个历史位置的 key 计算匹配分数，选出最相关的位置；然后再读取这个位置对应的 value 参与输出。只保存 value 时，无法判断应该选择哪个位置；只保存 key 时，虽然能找到位置，却没有该位置的 value 可用于生成输出。因此，KV cache 必须保存一一对应的 key/value 对。

    KV cache 为什么能避免重复计算¶

    如果不保存历史 K/V，decode 每生成一个 token，都要重新读取或计算所有历史 token 的 K/V。上下文越长，重复工作越多：

    不使用 KV cache
生成第 1 个 token：计算历史 1..N 的 K/V
生成第 2 个 token：再次计算历史 1..N 的 K/V，再计算新位置
生成第 3 个 token：再次计算历史 1..N+1 的 K/V，再计算新位置

    KV cache 把已经得到的 key 和 value 保存下来。下一轮 decode 只需为新 token 计算新的 K/V，历史部分直接复用：

    使用 KV cache
prefill：一次计算并保存历史 1..N 的 K/V
生成第 1 个 token：读取历史 KV，只追加新位置
生成第 2 个 token：继续读取和追加

    代价是 KV cache 会随上下文长度增长，并占用大量快速内存。真实服务因此可能把暂时不用的 KV 从 GPU 显存迁移到主存、SSD（固态硬盘），甚至远程存储。这类移动通常称为 offload（卸载）；需要继续计算时再 restore（恢复）。

    本实验没有 GPU，offload 路径是：CPU 用户页中的 KV -> xv6 文件系统；restore 路径是：xv6 文件系统 -> 新申请的 CPU 用户页。硬件层次虽然简化，但下面三个核心问题没有变化：

    1. 原来的快速层副本必须释放，否则无法证明真正依赖恢复；
    2. 恢复的数据必须完整、顺序正确且属于当前请求；
    3. 存储 I/O（输入/输出）和计算能否重叠，会影响端到端延迟。

    每个 kv_entry 包含 8 个整数 key 和 8 个整数 value。一个 int 类型（整数类型）在 xv6 中占 4 字节，一个请求保存 32 个 token，因此：

    sizeof(struct kv_entry) = (8 + 8) * 4 = 64 字节
AI_KV_FILE_BYTES       = 32 * 64 = 2048 字节

    AI_KV_FILE_BYTES 表示一个请求的完整 KV cache 写入文件时应占 2048 字节。

    你现在应当理解

    KV cache 是请求执行过程中产生的中间状态，不是模型参数，也不是 buffer cache。AI 附加题要求把它写入文件系统、释放原页并从文件恢复；Lab3 原题任务二（bcache） 中的 buffer cache 是内核用于缓存磁盘块的另一层机制。

    检查理解：KV cache、模型缓存和 buffer cache 有什么区别？

    KV cache 保存某个请求的 K/V；模型缓存复用共享只读模型或 embedding 分片；buffer cache 是 xv6 内核对磁盘块的缓存。三者处在不同层次，内容、所有权和生命周期都不同。

    三类核心数据不要混淆¶

    数据 来源 推理时是否修改 共享范围 生命周期 本实验表示 主要优化问题
    模型参数 训练完成后的固定参数 否 多请求、多 worker 共享内容 跨请求长期存在 m00～m36 减少重复文件读取
    embedding 分片 token 到向量的查表数据 否 多请求、多 worker 共享内容 跨请求长期存在 e00～e36 利用只读数据局部性
    KV cache 当前请求 prefill 产生 是 请求私有 从 prefill 延续到 decode KV 临时文件中的 2048 字节记录 完整持久化、隔离、顺序恢复
    query 当前请求计算产生 是 请求私有 当前请求内 workspace.query 与恢复后的 key 做匹配

    “共享内容”不等于“必须共享可写内存”。学生实现可以采用 worker 私有模型缓存，避免跨进程同步；只要每个缓存条目的内容都来自第一次真实文件读取，仍然利用了同一 worker 内的重复访问。

    本实验保留了什么，又简化了什么¶

    方面 真实推理服务 本实验
    模型规模 可能有数十亿参数、多个 GB 74 个 1024 字节分片
    计算 浮点/低精度矩阵算子，常用 GPU CPU 上的确定性整数计算
    attention 缩放点积、softmax、多头等 8 维点积、选最高分 value
    KV 层次 GPU 显存、主存、SSD、远程存储 用户页与 xv6 文件系统
    并发单元 线程、进程或运行时 worker 独立 xv6 进程
    系统问题 数据加载、内存压力、缓存与 I/O 竞争 保留这些数据流和竞争关系

    因此，本实验不是缩小版大语言模型精度实验，而是缩小版 AI 推理系统数据路径实验。它用足够小的数据在教学环境中稳定运行，同时保留可观察的操作系统行为。

    一次请求的完整数据路径¶

    把前面的概念串起来，一次请求会按下面的顺序流转：

    1. modelprep 预先生成 m00～m36、e00～e36 和 aimeta（模型清单文件）
    2. worker 根据请求编号得到 token 和要访问的分片编号
    3. prefill 从文件加载模型/embedding 分片，生成 query、key、value
    4. 32 组 key/value 形成 2048 字节 KV cache
    5. KV cache 写入 xv6 文件系统
    6. 原 KV 用户页通过 sbrk(-PGSIZE)（调整进程数据区大小的系统调用）释放
    7. decode 前重新申请页面，并用 0xa5 覆盖整页
    8. 从文件系统把当前请求 KV 恢复到新页面
    9. 校验恢复字节数和 KV checksum
    10. query 与恢复后的 key 匹配，读取 value，产生请求输出
    11. baseline 与 student 逐请求比较输出
