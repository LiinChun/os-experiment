    模型加载与 KV 持久化实现¶

    具体任务与分值先看附加题要求。建议按模型单项、KV 单项、完整 student 通路的顺序实现；以下状态机和伪代码是实现提示，不指定最终数据结构。

    实验任务¶

    任务一：模型与 embedding 加载（6 分）¶

    本任务只修改 user/ai_student_model.c 和 user/ai_student.c 中模型加载相关标志。建议先让自己写出的低性能版本通过单项测试，再加入缓存；若一开始同时改变文件读取、缓存布局和统计，很难判断错误来自哪一层。

    本节学习目标

    你应当能够说明三个接口分别在何时调用、谁拥有缓存、一次缓存未命中怎样变为有效条目，以及缓存命中为什么不增加真实 I/O 字节数。

    三个接口的契约¶

    接口定义为：

    int ai_student_model_begin(struct ai_session *session);
int ai_student_model_load(struct ai_session *session, uint family,
                          uint shard, char *block, struct ai_io *io);
void ai_student_model_end(struct ai_session *session);
    接口 调用时机 输入 成功后必须成立 失败/结束要求
    begin worker 处理请求前一次 worker 已写入的 session 当前 worker 的加载状态可用 失败时仍能安全清理
    load prefill 每次需要分片时 family、shard、输出 block、I/O 统计 block 恰好含正确 1024 字节 返回负数，不提交假统计
    end worker 正常或失败退出前 当前 session 所有模型加载资源已释放 重复清理不得释放野指针

    struct ai_session 只属于一个 worker。你可以使用其中预留的 state 和 memory，也可以在学生文件内定义自己的状态结构；不要让多个进程依赖一个可写全局状态。

    这里的“worker 私有”有两个好处：一是无需为用户态缓存再设计跨进程锁；二是某个 worker 清理时不会让其他 worker 的指针失效。代价是多个 worker 可能各自缓存一份相同分片，这是允许的设计取舍。

    先画出重复访问，再决定缓存什么¶

    一个请求有 32 个 prefill 步骤，每一步加载一个模型分片和一个 embedding 分片。分片编号由请求、worker 和 step 经过取模得到，因此工作集只有 37+37 个文件，却会被 3×24×32 次步骤反复访问。

    先画一条简化时间线：

    请求 0：m00 e00, m01 e01, ...
请求 1：m01 e07, m02 e08, ...
请求 2：m02 e14, m03 e15, ...
          ^
          某些分片在后续请求再次出现

    你需要决定缓存的最小单位。无论选按分片、按 family 或其他合法组织，必须能回答：

    • 怎样把 (family, shard) 唯一映射到缓存位置？
    • 怎样区分“条目尚未加载”和“条目已加载但首字节恰好为 0”？
    • 缓存由谁申请，何时释放？
    • 一次文件读取中途失败时，条目应保持什么状态？

    一次缓存未命中的状态变化¶

    推荐把一个条目抽象成两部分：内容和有效性。这里的“有效位”是概念要求，不限定你必须使用某个具体 C 结构。

    初始：valid = false，内容不可使用
  |
  | 生成文件名，open，精确读取，逐字节校验
  v
全部成功：写入正确内容，valid = true，提交真实 I/O 字节数
  |
  | 后续再次请求同一分片
  v
缓存命中：复制内容到 block，不执行文件读取，不增加 I/O 字节数

    如果 open()、read() 或校验失败，条目必须保持无效。不能先设置有效位再读取，否则另一次调用可能使用半写入内容。

    block 是调用者提供的输出缓冲区。即使内部缓存命中，也要把正确的 1024 字节交给 block，因为 shard_feature() 随后会从这里计算特征并再次校验。

    推荐的实现顺序¶

    1. 先原样写出一个能通过校验的 open -> read_exact -> close 版本，确认理解接口；
    2. 画出 3 个 worker 对 74 个只读分片的访问时间线，找出重复读取；
    3. 决定缓存粒度：按分片、按 family，还是整个 worker 工作集；
    4. 明确“未加载”和“分片内容恰好全零”不能用同一种状态表示；
    5. 处理初始化失败、读取失败和正常结束三类清理路径；
    6. 只有真实文件读取完整并校验后，才设置有效标志和增加 I/O 计数。

    下面是引导性伪代码，关键的数据布局、有效位表示和失败回滚需要你完成：

    load(session, family, shard, block, io):
    检查 family 与 shard 范围
    index = 把两类分片映射到统一索引
    if cache[index] 尚未有效:
        从对应文件精确读取到 cache[index]
        校验全部字节
        标记有效，并累计真实读取字节数
    把 cache[index] 的内容复制到 block

    伪代码故意没有给出：缓存对象怎样分配、两类分片怎样编号、有效位怎样存放、失败时怎样回滚。这些正是模型加载附加题要求学生设计的部分。

    必须保持的不变量¶

    不变量 为什么需要
    首次有效数据来自 xv6 文件 保证真实存储路径参与实验
    block 每次都是正确 1024 字节 保证 prefill 输入不变
    只有真实读取才增加 *_read_bytes 让指标能区分缓存命中和 I/O
    条目完整校验后才有效 防止使用部分读取或损坏数据
    session 只由当前 worker 使用 避免跨进程可写状态混淆
    end 回收所有动态资源 防止多轮测试耗尽内存或 fd

    常见错误

    • 直接用 ai_byte() 填充 block，没有文件 I/O；
    • 每次返回缓存命中也增加 model_read_bytes；
    • 把调用者的栈上 block 地址长期保存；
    • 申请较大对象放在 xv6 单页用户栈上；
    • begin 失败后 end 再次释放同一资源。
    实现前自检：第二次加载同一分片时，哪些动作可以省略，哪些不能？

    可以省略重新生成文件名、open/read/close、文件内容校验和真实 I/O 计数；不能省略把正确 1024 字节交给本次调用的 block，也不能改变请求看到的内容。

    单项验证¶

    在 Linux 终端运行：

    ./grade-ai "AI 模型"

    或在 xv6 shell 运行：

    modelprep
aimodeltest

    看到 AIMODELTEST: verify OK shards=74 后，再将 AI_MODEL_TASK_IMPLEMENTED 改为 1。该测试只证明模型任务接口正确，完整 student 通路仍需要 KV 附加题。

    如果测试报告 family 或 shard 错误，先检查二元组到缓存位置的映射；若第一次正确、第二次错误，重点检查有效位和复制方向；若输出正确但 I/O 字节数过大，检查缓存命中是否仍走了文件读取或重复计数。

    任务二：KV 持久化与恢复（8 分）¶

    KV 附加题不仅是“会调用 write() 和 read()”。它要求你维护一个跨越多个请求、先写后读的文件生命周期，并保证任意时刻都知道当前处于哪个阶段。

    本节学习目标

    你应当能够画出 KV session 状态机，解释一条 2048 字节记录何时算提交成功，并说明多 worker 文件隔离、请求顺序和错误路径怎样保持一致。

    七个接口组成一个状态机¶

    阶段 主要接口 输入或状态 成功后的状态
    worker 初始化 ai_student_kv_begin worker 编号、请求总数 文件名、fd 初值、计数器已初始化
    开始写 ai_student_kv_begin_write 已初始化 session 写入资源已准备，下一条为 request 0
    写一条 ai_student_kv_store request、KV 页、I/O 统计 当前记录完整持久化
    结束写 ai_student_kv_end_write 全部请求已写 写 fd 已关闭，文件边界稳定
    开始读 ai_student_kv_begin_read 完整持久化文件 从第一条记录开始恢复
    读一条 ai_student_kv_restore request、新 KV 页、I/O 统计 当前记录完整填入新页
    清理 ai_student_kv_end 任意可清理状态 fd 关闭、临时文件删除、状态失效

    合法调用顺序为：

    begin
  -> begin_write
  -> store(0), store(1), ... store(requests-1)
  -> end_write
  -> begin_read
  -> restore(0), restore(1), ... restore(requests-1)
  -> end

    store 和 restore 必须分别按 0, 1, ..., session->requests - 1 顺序处理。当前 aikvtest 会在每一步故意提交负数、越界、跳号、已完成或重复的 request；这些调用必须返回负数，不改变文件位置、预期的下一编号、I/O 统计或传入的 KV 页面。拒绝非法请求后仍要能继续处理当前合法编号，不得把一次拒绝当作文件 I/O 失败而破坏 session。阶段错乱也必须拒绝或安全处理；尚未结束写阶段就开始读可能看到不完整文件。

    文件组织与顺序为什么相关¶

    baseline 为每个请求创建独立文件，位置由文件名决定。student 可以保留这种组织，也可以减少文件数量。一个常见方向是每 worker 使用一个顺序文件：写阶段按 request 0、1、2 追加，关闭后重新打开，再按相同顺序读回。

    顺序文件的关键不变量是：

    第 request 条记录起点 = request * AI_KV_FILE_BYTES

    但 xv6 用户态没有课程外常见的任意 lseek() 接口可供随意跳转，所以更自然的做法是让读写调用严格按请求顺序前进。这里给出的是约束和一种思考方向，不限定最终数据结构。

    无论采用多少文件，都必须确保 worker 0、1、2 不写到同一可变区域。ai_student_kv_name() 可以生成带 worker 编号的短名称，例如 kvs0；学生还要自行维护文件描述符和当前请求状态。

    多 worker 文件命名

    若三个 worker 都写 kvs0，内容会互相覆盖。不要因为进程地址空间隔离，就误以为文件系统内容也会自动隔离；路径名相同指向的是同一个文件。

    短写、短读与“完整提交”¶

    一条 KV 记录固定为 AI_KV_FILE_BYTES = 2048 字节。精确写入可以抽象为：

    remaining = AI_KV_FILE_BYTES
p = kv
while remaining > 0:
    n = write(fd, p, remaining)
    if n <= 0:
        返回失败，记录尚未提交
    p += n
    remaining -= n

增加 kv_write_bytes
推进下一请求序号

    精确读取使用同样循环，只把 write 换成 read。三种返回情况含义不同：

    • n > 0：本次完成 n 字节，更新指针和剩余长度；
    • n == 0：读时通常表示提前到达文件末尾，无法得到完整记录；
    • n < 0：系统调用失败。

    只有循环正常结束，统计和请求序号才一起推进。可以把它理解为用户态的一次“小提交”：内容、统计和逻辑状态必须同时从“未完成”变成“完成”。

    常见错误：先推进状态，再执行 I/O

    如果写到一半失败但请求序号已经加一，清理或重试会把半条记录当成完整记录。恢复阶段的所有边界都会随之错位。

    错误路径也属于接口设计¶

    建议为 fd 规定明确的无效值，并在每次 open() 前后写出状态变化：

    初始：fd 无效
open 成功：fd 有效，由 session 拥有
close 成功：立即恢复为无效
end：只关闭仍有效的 fd，再删除当前 worker 的临时文件

    错误路径至少检查：

    • open() 失败时不能关闭未初始化 fd；
    • write() 中途失败时不能累计完整记录字节数；
    • end_write() 失败后 end() 仍应能清理残留资源；
    • begin_read() 打开失败时不能把 session 标成可恢复；
    • read() 中途失败时不能推进下一请求序号；
    • end() 不能二次关闭或二次释放同一资源。

    引导性伪代码¶

    下面只给出状态要求，不给出完整 session 布局和文件组织答案：

    store(session, request, kv, io):
    检查当前阶段是 WRITE
    检查 request 是预期的下一条
    循环 write，直到完整写入 AI_KV_FILE_BYTES
    完整成功后增加 kv_write_bytes
    更新下一写请求序号

restore(session, request, kv, io):
    检查当前阶段是 READ
    检查 request 是预期的下一条
    循环 read，直到完整读回 AI_KV_FILE_BYTES
    完整成功后增加 kv_read_bytes
    更新下一读请求序号

    你仍需要自行决定：阶段怎样编码、fd 放在哪里、何时创建或截断文件、失败后怎样回滚、end() 如何判断哪些资源仍有效。

    不可破坏的不变量¶

    不变量 被什么检查
    每请求完整写入 2048 字节 kv_write_bytes 增量
    原 KV 页在恢复前释放 workload 固定控制流
    恢复发生在新申请且已污染页面 memset(0xa5) + KV checksum
    每请求完整读取 2048 字节 kv_read_bytes 增量
    非法 request 被拒绝且无副作用 aikvtest 逐次尝试负数、越界、跳号、已完成、重复编号，并检查 KV 内容、I/O 统计与后续合法操作
    请求顺序和内容一致 aikvtest 的顺序校验及 KV checksum、compare 的逐请求输出
    worker 之间不覆盖 多 worker compare
    临时资源最终回收 多轮测试和结束路径
    实现前自检：写到 1200 字节时失败，请求序号和 kv_write_bytes 应怎样变化？

    二者都不应按完整记录推进。函数应返回失败，让上层终止本次通路；session 仍要保留足够状态，使 end() 能关闭 fd 并删除不完整临时文件。

    单项与端到端验证¶

    先运行：

    ./grade-ai "AI KV 持久化"

    或在 xv6 shell 中运行：

    modelprep
aikvtest

    aikvtest 通过时应同时出现 AIKVTEST: request order OK 和 AIKVTEST: verify OK requests=4 bytes=8192。这表示四条 2048 字节记录在写、读两个阶段各完成 8192 字节，并拒绝了非法请求；只看逐条 checksum 不能证明你检查了传入的 request。不要求在部分 I/O 失败后继续使用同一 session：应终止该通路并让 end() 清理；非法编号拒绝则必须保持当前 session 可继续执行。

    单项通过后将 AI_KV_TASK_IMPLEMENTED 改为 1，再运行：

    aiinfer student -w 3 -r 24
aiinfer compare -w 3 -r 24

    compare 不只比较总 checksum，还会逐 worker、逐请求检查输出。两条通路的 I/O 组织可以不同，推理语义必须相同。

    若 aikvtest 在单条记录就失败，先检查精确读写和 fd 模式；若少量请求正确、后续错位，重点检查请求序号与文件偏移；若单 worker 正确、多 worker 错误，重点检查文件命名和可写全局状态。
