    实验概述¶

    学术诚信与独立实践

    • 独立红线：请独立完成实验，主动避免阅读、使用他人或互联网上现成的实验代码。
    • 讨论边界：可以讨论思路，但不要交换代码。
    • AI 准则：可以使用 AI 辅助理解概念、梳理思路和定位问题，但不要提交本人未理解的生成内容。
    • 重在收获：课程看重的不只是测试结果，也看重你能否解释锁保护了什么、为什么优化后仍然正确。

    第一次现场考核注意事项

    第四次实验课将进行第一次实验现场考核。

    • 考核内容：
      • Lab1：XV6 与 Unix 实用程序；
      • Lab2：进程与系统调用；
      • Lab3：锁机制的应用。
    • 考核形式：助教与同学一对一问答，重点了解代码实现思路、关键设计和运行结果。
    • 考核目的：确认同学能够独立完成实验，并理解自己提交的代码，杜绝直接复制他人代码或提交未经理解的生成内容。

    请认真准备，确保能够清楚解释实验代码的实现与运行结果。

    实验说明

    本页主要说明 Lab3 要做什么、做到什么程度。

    • 能独立推进的同学，看完本页就可以开始。
    • 如果你对锁竞争、kalloc、buffer cache 还不熟，建议继续阅读 实验原理 和 实验实现 。
    • 开始前建议先复习理论课中的“多线程”“信号量”“死锁”。

    建议资料：

    • xv6 book 第 6 章 Locking；
    • xv6 book 第 3.5 节 Physical memory allocator；
    • xv6 book 第 8.1～8.3 节 Buffer cache。

    1. 实验目的¶

    • 理解锁在多核环境中的作用，以及锁竞争为什么会降低并发性能；
    • 熟悉 xv6 物理内存分配器 kalloc() / kfree() 的共享状态；
    • 熟悉 xv6 buffer cache 的查找、分配、引用计数和回收过程；
    • 在保持正确性的前提下，通过更细粒度的数据组织和锁设计减少争用；
    • 能够结合 #acquire、#fetch-and-add、kalloctest 和 bcachetest 判断优化是否有效。

    2. 实验学时¶

    4 学时

    3. 实验内容及要求¶

    Lab3 必做部分有两个任务：

    1. 优化物理页分配器，减少 kmem 锁竞争；
    2. 优化 buffer cache，减少 bcache 锁竞争。

    先分清两种命令行

    • Linux 终端：执行 git remote -v、git fetch <远程名> --tags、git checkout lock、git pull --ff-only <远程名> lock、make clean、make qemu、make grade；
    • xv6 shell：执行 kalloctest、bcachetest、usertests sbrkmuch、usertests。

    3.1 先保存 Lab2，再更新 Lab3 代码¶

    本实验基于 lock 分支。请在 Linux 终端中进入 xv6-oslabs-hitsz 目录，也就是能看到 Makefile 的目录。

    Step1：保存 Lab2 代码

    你当前工作区里的内容很可能还是 Lab2 的代码。如果不先处理干净就直接切到 lock 分支，可能会出现以下问题：

    • Lab2 和 Lab3 的改动混在一起，自己不容易分清；
    • 导出 commit.patch 时，可能把不属于 Lab3 的旧改动一起打进去；
    • 如果两个分支上的同名文件差异较大，切换时可能出现冲突。

    请先查看当前仓库状态：

    git status

    如果看到类似 nothing to commit, working tree clean，说明当前没有未提交修改，可以直接进行下一步。

    如果看到 modified、untracked files、Changes not staged for commit 或 Changes to be committed 等提示，说明当前还有未提交修改，请根据实际情况选择下面的一种处理方法：

    处理方法一：如果这些修改就是你已经完成的 Lab2 内容，请先提交：

    git add .
git commit -m "save lab2 work"

    处理方法二：如果你只是想临时保存这些修改，还不想提交，可以先暂存：

    git stash

    之后如果需要恢复这些未提交内容，再执行：

    git stash pop

    处理方法三：如果你确定当前修改都不需要保留，也可以强制切换：

    git checkout -f lock

    但这条命令会直接丢弃当前工作区里尚未保存的修改， 请谨慎使用 。只有在确认这些修改不需要保留，或已经另外备份后，才建议使用。

    确认 Lab2 代码已经保存好以后，执行下面的命令更新 Lab3 代码：

    3.2 任务一：优化内存分配器¶

    修改内存分配器（主要修改 kernel/kalloc.c） ，使多个 CPU 不必总是争用同一条空闲页链表和同一把 kmem.lock。

    原版 xv6 把所有空闲物理页都挂在同一条全局 freelist 上，并用 kmem.lock 保护对这条链表的操作。因此，多个 CPU 同时执行 kalloc() 或 kfree() 时，即使它们处理的是不同的物理页，也必须先获取同一把锁，操作只能一个接一个地进行。

    常见的优化 是把空闲页分散到各 CPU 的链表中，并为每条链表配置独立的锁：CPU 优先在自己的链表上分配或释放页面；只有本地链表没有空闲页时，才去其他 CPU 的链表借用页面。

    3.2.1 关于测评程序 kalloctest¶

    kalloctest（见 user/kalloctest.c）主要有两个测试：

    • test1：通过多进程并发申请和释放内存，观察 kmem* 相关锁的争用情况；
    • test2：在单进程下测试空闲页的申请与回收是否仍然正确。

    其中，test1 里频繁触发分配和释放的用户态接口是 sbrk()；它最终会通过 growproc()、uvmalloc()、uvmunmap() 等路径走到 kalloc() / kfree()。

    kalloctest 输出中最值得关注的是 kmem 相关锁的统计信息，尤其是 #fetch-and-add 和最终的 tot。其中，#fetch-and-add 表示获取锁时需要自旋等待的次数；tot 可以先把它理解成相关锁竞争情况的总和。这一题通常以 tot < 10 作为通过标准。若你想进一步了解 #acquire() 和 #fetch-and-add 的背景，可参考 xv6 中 Lock 的实现（选读）。

    3.2.2 测试要求¶

    1. 本题应在 多核 环境下测试，否则锁竞争数据没有意义；
    2. 请使用 initlock() 初始化锁，并要求锁名以 kmem 开头 ；这是因为课程提供的锁统计输出会专门关注 kmem 相关锁，锁名不符合要求时，你新增的这些锁可能无法被正确归到 kmem 的统计结果里；
    3. 在 Linux 终端 中执行 make qemu，进入 xv6 后，在 xv6 命令行 中运行 kalloctest，检查锁争用是否明显下降；
    4. 继续运行 usertests sbrkmuch，检查修改后系统是否仍能正确分配大量内存；
    5. 再运行 usertests，确保其仍然全部通过。

    3.3 任务二：优化磁盘缓存¶

    主要修改 kernel/bio.c。原版 xv6 让所有缓存块共享一把全局 bcache.lock：bget() 查找缓存块、为未命中请求选择可复用的 buf、更新块的元数据和引用计数，brelse() 减少引用计数并维护 LRU 链表时，都要先持有这把锁。因此，即使多个进程访问的是不同的磁盘块，它们也会在这些缓存管理操作上排队，bcache.lock 就成了并发访问时的主要竞争点。

    任务一可以按 CPU 分开管理空闲页，但 buffer cache 不能简单复制成“每 CPU 一套”。不同 CPU 可能访问同一个 (dev, blockno)，而同一磁盘块在缓存中最多只能有一份副本。你的设计需要同时解决“分散查找竞争”和“保持唯一副本”两个问题。

    3.3.1 关于测评程序 bcachetest¶

    bcachetest（见 user/bcachetest.c）会创建多个进程，反复读取不同文件，从而制造 bcache 相关锁的争用。

    在开始修改前，建议先进入 xv6，手动运行一次：

    bcachetest

    原版 xv6 下，bcache 的 #fetch-and-add 往往会比较大，这说明多个进程在缓存块查找、分配和回收时经常撞到同一把锁上。

    3.3.2 具体要求¶

    1. 不允许修改 NBUF 的大小；
    2. 不允许修改 struct buf 的数量；
    3. 同一个数据块在缓存中仍然最多只能有一份副本；
    4. 请修改 bget() 和 brelse()，让缓存区并发查询与释放时不必总等同一把全局锁；
    5. 如果你新增锁， 请使用 initlock() 初始化，并要求锁名以 bcache 开头 ；这是因为课程提供的锁统计输出会专门关注 bcache 相关锁，锁名不符合要求时，这些锁可能无法被正确归入 bcache 的统计结果里；
    6. 在 Linux 终端 中执行 make qemu，进入 xv6 后，在 xv6 命令行 中运行 bcachetest 和 usertests 检查结果。

    理想情况下，bcachetest 中相关锁的争用总和应尽量接近 0；测试代码要求本轮争用增量严格小于 500，恰好为 500 仍会失败。

    5. 建议完成顺序¶

    建议按下面的顺序进行：

    1. 切换到 lock 分支，并先成功启动 xv6。
    2. 先完成 kalloc 相关优化，跑通 kalloctest 和 usertests sbrkmuch。

    4. 最后补写 time.txt，执行 make grade，再完成实验报告。
