    VSCode 图形化界面调试指南（二）——系统调用¶

    这页能帮你做到什么

    看完这页后，你应该能完成三件事： 在 VSCode 中跟踪一次系统调用的执行过程 、 观察 ecall 前后的寄存器 / 汇编 / 页表信息 、 把用户态到内核态的切换过程看清楚 。

    先记住一条主线

    这一篇重点不是重新学习断点，而是沿着这条主线看清一次系统调用： 在用户态停住 → 找到 ecall → 看寄存器 / 页表 / 汇编变化 → 进入 usertrap 。

    开始前说明¶

    如果你还不熟悉断点、单步、变量查看，建议先看 VSCode 图形化界面调试指南（一） 。

    如果你已经能完成基础调试，并想继续看清一次系统调用是怎么从用户态进入内核态、再返回用户态的，这篇会更适合你。

    为了给同学们演示如何用 VSCode 图形化调试 xv6 的系统调用过程，我们在 VSCode 图形化界面调试指南（一） 的基础上，又录制了两个进阶演示视频：

    1. 【3. VSCode 调试系统调用过程（包含 pagetable 和汇编）】 https://www.bilibili.com/video/BV12P411J7xq?share_source=copy_web&vd_source=a822dcda3537564ccdd0bb45aa0afe33
    2. 【4. VSCode 调试系统调用——从内核到用户，再从用户返回内核】 https://www.bilibili.com/video/BV1ug411m7ir?share_source=copy_web&vd_source=a822dcda3537564ccdd0bb45aa0afe33

    1. ECALL 指令之前的状态¶

    首先，参考用户态程序调试从内核进入用户空间的user/ls.c。

    在第38行打上断点。

    点击“运行”，程序将自动运行到第38行并停止：

    在调试控制台输入display/10i $pc，让gdb持续自动显示从pc起的10条指令。

    在user/ls.asm反汇编文件中，可以看到ecall指令汇编地址是0x59c。

    接着，输入b *0x59c在ecall指令上打断点。再点击“运行”，程序自动停在了ecall指令那一行上。

    或者，也可以连续多次输入si（stepi命令），单步执行每一条汇编指令，直到程序停止ecall指令处。

    我们还可以输入info reg打印全部32个寄存器的值

    这里最值得先看的，是 a0 和 a1 这两个寄存器。它们保存了 ls 调用 fstat 时传入的参数：其中 a0 是文件描述符 fd ，a1 是接收 stat 结构体信息的指针。

    这时也可以输入 print/x $satp 或 p/x $satp ，查看 satp 寄存器的值，也就是当前页表所在的物理地址。

    satp寄存器给出的物理内存地址是0x8000000000087f48。

    如果还想进一步看 page table 的映射关系，需要切到 QEMU 界面（注意，是在 终端 ，不是调试控制台），输入 Ctrl-A C 进入 QEMU console，然后再输入 info mem 。

    上面打印出来的是用户程序ls的page table，非常小，只包含了5条映射关系。

    page table拓展知识

    在上图中，attr是PTE（页表，Page Table Entry）的标志位。

    • r：Readable，可读
    • w：Writable，可写
    • x：Executable，可执行
    • u：User，表明PTE_u标志位是否被设置，用户代码只能访问u标志位设置了的PTE。也就是如果有这个标志位，则说明这个page可以被运行在用户空间的进程访问。
    • a：Accessed，表明这条PTE是否被使用过。
    • g：Global
    • d：Dirty，表明这条PTE是否被写过。

    最后两条PTE的虚拟地址非常大（接近虚拟地址的顶端），它们分别是trapframe page和 trampoline page（详见xv6 book P24-26）。这两个PTE没有u标志位，用户代码不能访问它们。当进入supervisor mode时，才能够访问。可能有同学注意到，第二条PTE也没有u标志位，这是一个无效的page（guard page），以防止用户程序尝试使用过多的stack page。

    我们在kernel/memlayout.h头文件中，也可以看到trapframe的定义。

    // map the trampoline page to the highest address,
// in both user and kernel space.
#define TRAMPOLINE (MAXVA - PGSIZE)

    PGSIZE和MAXVA的定义在kernel/riscv.h。

    #define PGSIZE 4096 // bytes per page

// one beyond the highest possible virtual address.
// MAXVA is actually one bit less than the max allowed by
// Sv39, to avoid having to sign-extend virtual addresses
// that have the high bit set.
#define MAXVA (1L << (9 + 9 + 9 + 12 - 1))

    这样，就能计算出TRAMPOLINE的地址是1<<38 - 4096 = 0x3ffffff000，这个地址和上面用info mem命令查到的最后一条PTE是一样的。也就是，最后一条PTE正是TRAMPOLINE。

    2. ECALL指令之后的状态¶

    为了在程序执行到 trampoline.S 中 uservec 段的第一条指令时暂停，您可以在地址 0x3ffffff000 处设置断点。

    在 GDB 调试控制台中输入以下命令：

    b *0x3ffffff000

    请注意：如果你使用的是 riscv64-unknown-elf-gdb（而非 gdb-multiarch 或 riscv64-unknown-linux-gnu-gdb），则可以直接通过 stepi 命令跟踪 ecall 指令进入内核，无需在 0x3ffffff000 地址处设置断点。 这是因为：

    • riscv64-unknown-elf-gdb 用于调试裸机程序（如操作系统），能够正确处理特权级切换和汇编指令级别的调试。

    • riscv64-unknown-linux-gnu-gdb 则用于调试运行在 Linux 操作系统之上的用户态程序。

    点击“运行”，或者输入si单步执行ecall指令。

    从这里可以看到，已经进入了trampoline。

    如何知道第85行jr t0语句的地址是0x3ffffff08e？

    在调试控制台，输入x/40i $pc显示当前PC后面的40条指令，就可以看到jr t0对应的地址。

    也可以通过查看kernel.asm反汇编文件，在0000000080007000 <_trampoline>:段，可以看到jr t0相对uservec第一条指令位置偏移了0x8e，将0x3ffffff000 + 0x8e，就是0x3ffffff08e。

    trampoline 拓展知识

    user page table 和 kernel page table 对 trampoline page 的映射是相同的（虚拟地址都是 0x3ffffff000 ）。正因为如此，切换页表之后，CPU 仍然能继续在这段代码上执行；否则一旦切页表就可能因为找不到下一条指令而崩溃。这也是 trampoline page 的关键作用。

    trapframe 拓展知识

    user page table 中倒数第二个 PTE 的虚拟地址 0x3ffffffe00 对应的是 trapframe page 。它由内核预先设置好，用来保存当前进程的用户态寄存器。这样一来，内核在进入 C 代码并覆盖寄存器之后，后续仍然可以把这些寄存器恢复回去。

    如果你想进一步看里面保存了什么，可以继续查看 proc.h 中的 trapframe 结构体。

    先记住这个结论

    从上面的过程可以先记住两件事。

    第一，ecall 本身由硬件完成三件关键事情：

    1. 把执行模式从 user mode 切到 supervisor mode。
    2. 把当前 PC 保存到 SEPC 寄存器，也就是保存 ecall 在用户空间的位置。之后内核会再把它保存到 trapframe->epc 中。
    3. 跳转到 STVEC 指向的入口。对 xv6 来说，这个入口就是 trampoline 中的代码。

    第二，在真正进入内核 C 代码之前，uservec 这一段汇编还会继续完成三件事：

    1. 保存用户寄存器。
    2. 从 user page table 切换到 kernel page table。
    3. 把 sp 切到 kernel stack ，为后续 C 代码准备好栈。

    其中，kernel satp 和 kernel stack 都是在 usertrapret 中提前准备好的。

    3. 汇编之后的 C 代码¶

    看到 usertrap 之后，执行流就已经进入内核的 C 代码了。对大多数同学来说，这一段会比前面的汇编更容易继续跟。

    如果你现在主要关心系统调用本身，可以在 syscall(); 这一行打断点，然后点击“运行”，让程序停在 syscall() 函数处。想继续深入的话，也可以顺着 usertrap() 往下分析。

    接下来进入 syscall.c 里的 syscall() ，就可以继续按普通的 VSCode 调试方式往下看。

    4. 一个简单的从用户到内核空间的调试方法¶

    如果你现在不想先跟完整段汇编，而是想更快地停到内核里的 C 代码，可以按下面这组步骤做。下面仍以 ls 中的 fstat 系统调用为例。

    Step1： 在终端执行 make qemu-gdb ，然后在 VSCode 中按 F5 连接。

    Step2： 点击“运行”，让 xv6 正常启动，直到 shell 出现 $ 提示符。

    Step3： 在调试控制台输入 interrupt ，先把执行流停住。

    Step4： 在 kernel/trap.c:128 打断点，再继续运行。

    Step5： 在 xv6 的 shell 中输入 ls ，程序会停在 kernel/trap.c:128 处。

    Step6： 删除原有内核态断点，并在调试控制台输入 file user/_ls ，切换到 ls 的调试符号。

    Step7： 打开 user/ls.c ，在 main() 第 78 行打断点，点击“运行”。

    Step8： 再在 ls.c 第 38 行打断点，继续运行，让程序停在执行 fstat 系统调用之前。

    Step9： 在调试控制台输入 file kernel/kernel ，切回内核调试符号。

    Step10： 在 syscall.c 中 syscall(); 所在位置打断点，继续运行。程序就会停在系统调用对应的内核 C 代码处。

    到这里，你就可以根据自己的需要，继续分析后续执行流程了。
