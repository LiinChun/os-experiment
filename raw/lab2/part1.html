    实验概述¶

    学术诚信与独立实践

    • 独立红线 ：请独立完成实验，主动避免阅读、使用他人或互联网上现成的实验代码。
    • 讨论边界 ：遇到困难时，请先自己分析、实现、调试；可以讨论思路，但不要交换代码。
    • AI 准则 ：可适度使用 AI 辅助理解概念、梳理思路、定位问题；不要直接提交本人未充分理解的 AI 生成内容。
    • 重在收获 ：课程看重的不只是结果，更看重你在实践中形成的理解与能力。

    实验说明

    • 本页主要说明 Lab2 要做什么、做到什么程度。
    • 能独立推进的同学，看完本页就可以开始。
    • 如果你对系统调用的基本过程，以及 exit / wait / yield 的语义还不熟，建议继续阅读 实验原理 和 实验实现 。
    • 开始前建议先复习理论课中的“导论与操作系统结构”和“进程与线程：进程”。

    建议资料：

    • 我校讲解视频：XV6（二）进程管理
    • 配套课件：课程 PPT
    • MIT 视频：Lecture 3 - OS Organization and System Calls
    • MIT 视频：Lecture 6 - Isolation & System Call Entry/Exit
    • 参考书：xv6 book 第 4 章 4.3、4.4 节
    • 如需用 GDB 跟踪系统调用过程，可参考 系统调用调试指南 。

    1. 实验目的¶

    • 理解 xv6 中系统调用从用户态进入内核、再返回用户态的基本过程。
    • 理解 exit、wait、yield 与进程状态、父子关系、调度切换之间的关系。
    • 练习修改系统调用接口、分发逻辑和内核主体函数。
    • 为后续继续阅读和修改 xv6 内核代码打下基础。

    2. 实验学时¶

    本实验为 4 学时。

    3. 实验内容及要求¶

    可以参考 MIT 的 Lab: System calls 与 Lab: Trap 的部分说明， 但请以本指导书为准 。

    先分清 3 种命令行

    • Linux 终端 ：执行 git remote -v、git fetch <远程名> --tags、git checkout syscall、git pull --ff-only <远程名> syscall、make clean、make qemu、make qemu CPUS=1、./grade-lab-syscall yield、make grade。
    • xv6 命令行：执行 exittest、waittest、yieldtest。
    • GDB 命令行：本实验不是硬性要求；如果你想跟踪系统调用过程，可按调试指南自行使用。

    3.1 先保存 Lab1，再更新 Lab2 代码¶

    本实验基于 syscall 分支。由于 Lab2 的基础任务和附加题评测脚本已有更新，即使你之前已经克隆过实验仓库，也需要先同步远程仓库中的最新分支和标签。

    下面这些命令都在 Linux 终端 中执行。请先进入 xv6-oslabs-hitsz 目录，也就是能看到 Makefile 的目录。

    Step1：保存 Lab1 代码

    你当前工作区里的内容很可能还是 Lab1 的代码。如果不先处理干净就直接切到 syscall 分支，后面容易出现几种问题：

    • Lab1 和 Lab2 的改动混在一起，自己都不容易分清；
    • 之后导出 commit.patch 时，可能把不属于 Lab2 的旧改动也一起打进去；
    • 如果两个分支上同名文件差异较大，切换时还可能出现冲突。

    请先查看当前仓库状态：

    git status

    如果看到类似 nothing to commit, working tree clean，说明当前没有未提交修改，可以直接继续执行后面的 Lab2 更新命令。

    如果看到 modified、untracked files、Changes not staged for commit 或 Changes to be committed 等提示，说明当前还有未保存到提交里的修改，请先按下面三种方法之一处理：

    处理方法一：如果这些修改就是你已经完成的 Lab1 内容，请先提交：

    git add .
git commit -m "save lab1 work"

    处理方法二：如果你只是想先临时收起来，还不想提交，可以先暂存：

    git stash

    之后如果需要把这些未提交内容再拿回来，再执行：

    git stash pop

    处理方法三：如果你非常确定当前这些修改都不要了，也可以强制切换：

    git checkout -f syscall

    但这条命令会直接丢弃当前工作区里尚未保存的修改， 请谨慎使用 。只有在你已经确认这些改动不需要保留，或者已经另外备份过时，才建议这样做。

    确认 Lab1 代码已经保存好以后，再执行下面的命令更新 Lab2 代码：

    step2： 确认课程实验仓库对应的远程名

    git remote -v
# 找到指向课程实验仓库的远程名。多数同学是 origin；如果你的是 upstream，就改成 REMOTE=upstream。
REMOTE=origin

    例如，执行 git remote -v 后可能看到：

    origin    https://gitee.com/你的用户名/xv6-oslabs-hitsz.git (fetch)
origin    https://gitee.com/你的用户名/xv6-oslabs-hitsz.git (push)
upstream  https://gitee.com/ftutorials/xv6-oslabs-hitsz.git (fetch)
upstream  https://gitee.com/ftutorials/xv6-oslabs-hitsz.git (push)

    这时课程实验仓库对应的远程名是 upstream，所以上面的命令应改为 REMOTE=upstream。

    step3： 拉取最新代码，并切换分支

    git fetch "$REMOTE" --tags
git checkout syscall
git pull --ff-only "$REMOTE" syscall
make clean

    其中，git checkout syscall 会切换到 Lab2 使用的本地分支；git pull --ff-only "$REMOTE" syscall 会从该远程拉取 syscall 分支的最新提交，并更新到本地当前的 syscall 分支；make clean 清理旧编译结果和部分中间文件。这样可以确保本地拿到最新的基础任务和附加题评测脚本。

    3.2 任务一：在 exit 时打印父子进程信息¶

    这一题围绕 exit 系统调用展开。它对应的接口是：

    void exit(int status)

    这个函数的作用是：让当前进程退出。更具体地说，它会清理退出前需要释放的资源、处理父子进程关系、把当前进程状态改成合适的退出状态，然后离开当前进程的执行流， 不会返回 。

    本题要求你在 exit 执行流程的合适位置，打印：

    • 当前进程退出时的父进程信息；
    • 当前进程退出时的各个子进程信息。

    请注意：

    • 请使用课程提供的 exit_info 输出，不要直接用 printf；
    • 进程状态统一按题目要求输出为小写。

    也就是说，exit 要输出父进程信息和各个子进程信息，格式如下：

    proc PID exit, parent pid PID, name NAME, state STATE
proc PID exit, child CHILD_NUM, pid PID, name NAME, state STATE

    其中各字段含义如下：

    • PID ：进程号；
    • CHILD_NUM ：这是第几个子进程，从 0 开始编号；
    • NAME ：进程名；
    • STATE ：进程状态，例如 sleep、run、runble；其中 runble 是课程输出函数对 RUNNABLE 状态的固定拼写。

    实验提供了用户程序 exittest（见 user/exittest.c）用于测试该任务。不要修改这个测试程序。

    当功能正确时，运行 exittest 后应能看到类似输出：

    $ exittest
exit test
[INFO] proc 3 exit, parent pid 2, name sh, state sleep
[INFO] proc 3 exit, child 0, pid 4, name child0, state sleep
[INFO] proc 3 exit, child 1, pid 5, name child1, state sleep
[INFO] proc 3 exit, child 2, pid 6, name child2, state sleep
$ [INFO] proc 5 exit, parent pid 1, name init, state runble
[INFO] proc 4 exit, parent pid 1, name init, state run
[INFO] proc 6 exit, parent pid 1, name init, state run

    这段输出可以这样理解：

    • 前 4 行都在描述 proc 3 退出这一刻看到的信息：第一行打印它的父进程是 sh；后面三行打印它当时的 3 个子进程 child0、child1、child2。
    • 后面 3 行则是在这些子进程自己退出时打印的。此时它们的父进程已经不再是原来的 proc 3，而变成了 pid 1 的 init。
    • 之所以后面这 3 行没有继续打印子进程信息，是因为 proc 4、proc 5、proc 6 在这个测试里本身没有再创建新的子进程；它们退出时只能打印自己的父进程信息。

    也就是说，这组输出正好说明了：父进程先退出后，它原来的子进程会被重新交给 init 进程管理。

    3.3 任务二：为 wait 增加非阻塞选项¶

    这一题围绕 wait 系统调用展开。原来的接口是：

    int wait(int *status)

    它的作用是：让父进程等待子进程退出，并在成功回收某个子进程时返回该子进程的 pid，同时把退出状态写到 status 指向的位置。

    本题要求你把它改成：

    int wait(int *status, int flags)

    其中：

    • status ：用于接收子进程退出状态；
    • flags ：用于控制这次 wait 是阻塞还是非阻塞。

    语义如下：

    • flags == 0 ：保持原来的阻塞等待；
    • flags == 1 ：如果当前没有可回收的僵尸子进程，就不要睡眠，而是直接返回 -1。

    也就是说，这一题的重点不是“新增一个完全不同的函数”，而是让同一个 wait 同时支持两种行为。

    用户态接口课程组已经帮你改好；你需要完成的是内核态部分的修改。

    3.4 任务三：实现 yield 系统调用¶

    这一题要求你新增一个系统调用 yield。它的核心作用是：让当前进程 主动让出 CPU ，从而让调度器有机会切换到其他可运行进程。

    请注意，yield 的含义不是“退出进程”，而是“暂时不继续占用 CPU”。当前进程后面仍然可能再次被调度回来，继续向后执行。

    除了补齐系统调用本身，这一题还要求你打印与调度相关的三类信息：

    Save the context of the process to the memory region from address 0x??? to 0x???
Current running process pid is ??? and user pc is 0x???
Next runnable process pid is ??? and user pc is 0x???

    这三行分别表示：

    • 当前进程的内核线程上下文会被保存到哪一段内存；
    • 当前正在运行进程的 pid 以及它陷入内核前的用户态 pc；
    • 下一个可能被调度运行进程的 pid 以及它对应的用户态 pc。

    也就是说，你不仅要补齐系统调用入口，还要在合适的位置打印：

    • 当前进程内核线程上下文保存到的地址范围；
    • 当前进程的 pid 和用户态 pc；
    • 下一个将被调度进程的 pid 和用户态 pc。

    请注意：

    • 当前实验分支已经把 yieldtest 加入 Makefile 的 UPROGS 中；开始实现前请确认该项仍然存在；
    • 手动测试 yieldtest 时，请在 Linux 终端 中使用 make qemu CPUS=1 启动 xv6。

    之所以要求 CPUS=1，是因为这一题的输出与调度顺序关系较大，单核环境更容易观察，也更容易和测试脚本对齐。

    4. 建议完成顺序¶

    建议按下面的顺序完成：

    1. 切换到 syscall 分支，同步最新代码，并先成功启动 xv6。
    2. 先完成任务一，理解 exit、父子关系和 reparent。
    3. 再完成任务二，理解 wait 为什么会阻塞，以及非阻塞逻辑加在哪里。
    4. 最后完成任务三，把系统调用的基本过程、trapframe、context、scheduler 串起来。
    5. 执行 make grade，再完成实验报告。
