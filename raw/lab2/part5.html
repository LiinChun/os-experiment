    附加题：AI Agent 沙箱 — 基于系统调用的进程隔离¶

    附加题评测

    本页内容全部属于 Lab2 附加题，不影响基础任务的 100 分。基础任务通过 make grade 评测；附加题通过 make grade-extra 单独评测，总分 20 分。

    注意

    本题为选做附加题，完成后可获得额外加分。但请确保你已经完成实验必做部分（任务一、二、三）后再开始本题。

    提示

    本节内容与 系统调用、进程控制 和 操作系统安全 密切相关。在开始实验前，建议先回顾系统调用的完整流程（从用户态到内核态再返回），以及 fork、exec、open 等关键系统调用的实现细节。

    推荐阅读：

    • xv6 book Chapter 4: Traps and system calls
    • [kernel/syscall.c] 中 syscall() 的分发机制
    • [kernel/proc.c] 中 fork() 和 exit() 的实现

    1. 背景：AI Agent 为什么需要沙箱？¶

    假设你正在构建一个 AI Agent，它需要执行用户提供的代码、运行 shell 命令、读取文件内容来完成复杂任务。但 Agent 运行的是不可信的外部命令——如果它执行了 :(){ :|:& };:（fork bomb）、或者 rm -rf /、或者偷偷读取了 /etc/shadow，后果不堪设想。

    在实际操作系统中，Linux 提供了 seccomp（secure computing mode）来限制进程可用的系统调用，cgroups 来限制资源使用，namespace 来做文件系统隔离。但在 xv6 中，这些机制都不存在。

    本附加题的任务： 在 xv6 中为进程实现一套轻量级的沙箱机制，包含 系统调用白名单、审计日志、进程资源限制 三个核心模块，让 OS 有能力限制一个"AI Agent 进程"的行为。

    2. 实验学时¶

    本附加题为 2~4 学时（选做）。

    3. 实验内容及要求¶

    本次附加题在 syscall 分支 上进行，你需要基于已经完成的实验二代码继续开发。在原有的系统调用框架上，实现以下三个模块：

    3.1 任务一：系统调用白名单（Syscall Allowlist）¶

    要求： 实现一个系统调用白名单机制，使进程只能调用白名单内的系统调用，白名单外的系统调用将被内核拦截并返回 -1。

    你需要：
    1. 在 struct proc（kernel/proc.h）中增加一个用于记录白名单的字段（提示：位掩码（bitmask）是一种简洁的方式，64 位足以覆盖 xv6 所有系统调用）
    2. 实现一个新的系统调用 seccomp_ctl，用于设置当前进程的系统调用白名单
    3. 修改 kernel/syscall.c 中的 syscall() 函数，在执行系统调用之前检查白名单
    4. 确保白名单外的系统调用被拦截时，不执行 对应的系统调用处理函数，直接返回 -1

    场景示例： 一个 AI Agent 进程只应该 write（写日志）和 exit（退出），调用 fork、open、exec 等系统调用都应当被拒绝。

    3.2 任务二：审计日志（Audit Log）¶

    要求： 实现审计日志功能，记录所有被白名单拦截的系统调用。

    你需要：
    1. 在 struct proc 中增加一个审计日志缓冲区（提示：固定大小的数组即可，如 32 个条目）
    2. 当系统调用被白名单拦截时，将系统调用号记录到审计日志中
    3. 实现另一个新的系统调用 seccomp_getlog，让用户态程序可以获取审计日志内容

    审计日志的内容： 每个条目至少包含被拦截的系统调用号。日志按时间顺序记录，用户态程序可以通过 seccomp_getlog 获取日志缓冲区的内容。

    3.3 任务三：进程资源限制（Process Resource Limits）¶

    要求： 限制进程可创建的子进程数量，防止 Agent 进程通过 fork bomb 耗尽系统资源。

    你需要：
    1. 在 struct proc 中增加子进程计数和最大子进程数限制字段
    2. 扩展 seccomp_ctl 系统调用的功能，使其支持设置子进程数上限
    3. 修改 fork() 函数，在创建子进程前检查上限
    4. 当一个子进程被 wait() 回收时，相应减少计数

    注意： 需要考虑白名单以及资源限制在 fork 时的继承关系——子进程应当继承父进程的沙箱配置。

    4. 实验实现提示¶

    提示

    以下是一些实现方向的提示，但完整的实现需要你自己完成。不会给出逐行代码。

    • 位掩码设计：每个系统调用号对应一个 bit，seccomp_mask 的第 N 位为 1 表示允许第 N 号系统调用。设置时通过 seccomp_ctl(0, mask) 传入位掩码；传入 0 会禁止所有普通系统调用，如需恢复全部权限可传入 ~0UL。
    • syscall() 分发函数：在 syscall() 中，在通过中断向量表调用处理函数前，先检查当前进程的 seccomp_mask。如果设置了 mask 且当前系统调用号不在 mask 中，则直接返回 -1 并记录审计日志。
    • seccomp_ctl 和 seccomp_getlog 应该 始终可用，即使设置了白名单也能被调用，否则进程将无法恢复或查询日志。
    • 子进程的沙箱配置应当继承自父进程，这样父进程创建的子进程也会同样受到限制。

    4.1 新增系统调用接口¶

    建议的接口设计如下：

    // op: 操作码
//   0 — 设置系统调用白名单位掩码（arg 为位掩码）
//   1 — 设置最大子进程数（arg 为最大数量）
int seccomp_ctl(int op, uint64 arg);

// buf: 存放审计日志条目的缓冲区（至少 32 * sizeof(uint64) 字节）
// len: 传入缓冲区容量，返回实际写入的条目数
int seccomp_getlog(uint64 *buf, int *len);

    4.2 参考流程¶

    任务一流程：

    实验分支已经提供 kernel/syscall.h 中的系统调用号、user/user.h 中的用户态声明、user/usys.pl 中的入口，以及 Makefile 中的 seccomptest。不要重复定义这些骨架。

    在内核部分：

    • 在 kernel/syscall.c 中添加 extern 声明和 syscalls 数组项
    • 在 kernel/sysproc.c 中实现 sys_seccomp_ctl 函数
    • 修改 kernel/syscall.c 的 syscall() 函数，添加白名单检查逻辑
    • 在 struct proc 中添加白名单字段，并在 allocproc() 中初始化

    任务二流程：

    • 在 struct proc 中添加审计日志缓冲区
    • 在白名单检查逻辑中拦截系统调用时，同步记录审计日志
    • 在 kernel/sysproc.c 中实现 sys_seccomp_getlog 函数
    • 在 kernel/syscall.c 中补齐 sys_seccomp_getlog 的 extern 声明和分发表项

    任务三流程：

    • 在 struct proc 中添加子进程计数和上限字段
    • 在 kernel/sysproc.c 中扩展 sys_seccomp_ctl 以支持设置子进程上限
    • 在 kernel/proc.c 的 fork() 中添加检查逻辑
    • 在 fork() 中让子进程继承父进程的沙箱配置
    • 在 wait() 中回收子进程时递减计数

    5. 测试¶

    本页的测试说明和输出示例以代码仓库 syscall 分支对应的 syscall-26-fall-v2 标签为准。该标签提供了 seccomptest 用户级测试程序（见 user/seccomptest.c），并已将其加入 Makefile 的 UPROGS 中。

    完成附加题后，在 xv6 代码目录运行：

    make grade-extra

    该命令只评测附加题，总分 20 分。基础任务仍使用 make grade 评测，满分为 100 分。两个评测命令都会输出通过情况和得分；测试未通过不会使命令报错退出。

    make grade-extra 会先输出编译信息，再显示评分摘要。通过时终端输出示例如下（编译信息省略，耗时因机器而异）：

    == Test seccomp test ==
$ make qemu-gdb CPUS=1 LAB_SYSCALL_TEST=on
seccomp test: OK (2.6s)
    (Old xv6.out.seccomp_test failure log removed)
Score: 20/20

    其中 Old ... failure log removed 仅在此前有失败日志、本次测试通过时出现，表示旧失败日志已删除。Score: 20/20 表示通过当前附加题评测。

    评分摘要不会逐项显示 PASS。完整的 xv6 测试输出保存在代码目录的 xv6.out 中，可用 cat xv6.out 查看；也可以使用 make qemu CPUS=1 启动 xv6，在 xv6 的 shell 中输入 seccomptest 查看详细输出。因此，运行 make grade-extra 后看到上面的摘要，而不是下面的逐项输出，是正常现象。

    当前 seccomptest 检查白名单是否阻止 fork() 和 open()、审计日志是否非空，以及子进程数量限制和 wait() 回收后的计数更新。完成任务后，在 xv6 中运行 seccomptest，通过时输出如下：

    运行 seccomptest 需要设置 CPU 数量为 1，即使用 make qemu CPUS=1 启动 xv6。

    7. 思考题¶

    思考题

    (1) 白名单（allowlist）与黑名单（blocklist）在安全设计中各有什么优劣？在沙箱场景下为什么选择白名单？

    (2) 在我们的实现中，seccomp_ctl 和 seccomp_getlog 不受白名单限制。思考一下：如果这两个系统调用也被白名单限制，会发生什么问题？

    (3) 我们在任务三中只限制了子进程数量。如果要限制一个 Agent 进程的 最大内存使用量 和 最大打开文件数 ，应当修改哪些函数？这里的“最大打开文件数”是指单个进程持有的文件描述符数量，而不是系统全局文件表的容量。（提示：内存限制可查看 growproc()；单进程文件描述符限制可查看 fdalloc()、sys_close() 和 fork()。filealloc() 管理的是系统全局文件表。）

    (4) 如果把白名单设置后，进程无法调用 exec() 了，会出现什么问题？有什么办法可以在设置白名单之前完成必要的初始化？
